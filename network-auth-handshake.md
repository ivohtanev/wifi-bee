# Наблюдение на Wi-Fi authentication и handshake

Проверено на 29.10.2026 за текущата машина. За собствена мрежа или мрежа с разрешение за диагностика.

## Препоръка

**Най-бърз старт: airodump-ng за преглед на AP/клиентите и индикация за WPA handshake; Wireshark за подробно разглеждане на authentication, association и EAPOL.** За терминален поток само с интересните събития използвай TShark. За продължителен запис използвай dumpcap.

Това е практическа преценка за наличната конфигурация, а не измерен benchmark.

| Инструмент | Най-удобен за | Ограничение |
| --- | --- | --- |
| airodump-ng | Бърз списък на мрежи/клиенти, канал и индикатор за handshake | Не показва подробно всеки auth кадър |
| Wireshark | Графичен преглед на auth и handshake пакет по пакет | Изисква филтриране; дълъг live запис натрупва данни |
| TShark | Терминални събития и бъдещо добавяне на известия | Наличието на EAPOL не е автоматична проверка за пълен handshake |
| dumpcap | Запис с ротация на файлове | Анализът се прави отделно |
| Kismet | Постоянен обзор на повече устройства и мрежи през уеб интерфейс | Допълнителна настройка; не е намерен в текущия PATH |

Локално са намерени `wireshark`, `tshark`, `dumpcap`, `airodump-ng` и `iw`. TShark е версия **4.6.4**. Полетата за номер на EAPOL-Key съобщение, алгоритъм за authentication и status code са проверени в локалния списък с полета.

## 1. Използваме готовия скрипт

В работната папка:

```bash
sudo ./wifi-monitor.sh start
./wifi-monitor.sh status
```

Скриптът създава **wifi_mon** върху радиото на **wlp44s0**. Не е необходимо допълнително стартиране на `airmon-ng`.

За надеждно засичане на кратък handshake остани на канала на конкретния AP. Примерните BSSID `02:11:22:33:44:55` и канал `6` по-долу трябва да се заменят с реалните. При няколко радиа/SSID на рутера избери точния BSSID и неговия канал.

Двата интерфейса споделят физическо радио: ако NetworkManager свързва `wlp44s0` към друга мрежа, може да се получи конфликт при избора на канал. Скриптът не гарантира независими канали. Ползвай наличния USB интернет за връзката; при постоянен конфликт отделен USB Wi-Fi адаптер за мониторинга е по-надеждното решение.

## 2. Най-бързият преглед: airodump-ng

Кратък обзор на 2.4 и 5 GHz:

```bash
sudo airodump-ng --band abg wifi_mon
```

Виж BSSID, CH, ESSID и клиентите в долната таблица. Спри с `Ctrl+C`. Обхватът зависи от адаптера и регулаторните настройки; тази команда не е обзор на 6 GHz.

После наблюдавай и записвай само избраната мрежа:

```bash
mkdir -p captures
sudo airodump-ng --bssid 02:11:22:33:44:55 --channel 6 \
  --write captures/session --output-format pcap wifi_mon
```

В горната част следи за **WPA handshake: BSSID**. Това е удобна първоначална индикация; за диагностичен извод отвори записа във Wireshark. Първият запис обикновено е `captures/session-01.cap`; при повторни сесии номерът се увеличава.

За възпроизводим тест стартирай записа, после изключи и включи Wi-Fi на собствен телефон или лаптоп и го свържи към тестовата мрежа. Така наблюдаваш нормален обмен без изпращане на deauthentication кадри. Ако няма ново свързване, може да чакаш дълго без handshake.

## 3. Най-удобен подробен изглед: Wireshark

След спиране на airodump-ng можеш да разгледаш файла:

```bash
wireshark -r captures/session-01.cap
```

Или за наблюдение на живо първо задай канала:

```bash
sudo iw dev wifi_mon set channel 6
wireshark -i wifi_mon -k
```

Стартирай графичната програма като обикновен потребител. Ако няма права за capture, използвай записа от airodump-ng или dumpcap; настройката на capture правата е отделна стъпка.

В полето **Display filter** постави:

```text
wlan.bssid == 02:11:22:33:44:55 && (eapol || wlan.fc.type_subtype in {0x00 0x01 0x02 0x03 0x0a 0x0b 0x0c})
```

Това показва association/reassociation, authentication, disassociation/deauthentication и EAPOL за избрания AP. По-тесни филтри:

| Какво търсим | Display filter |
| --- | --- |
| Всички EAPOL пакети | `eapol` |
| WPA EAPOL-Key съобщения с разпознат номер | `wlan_rsna_eapol.keydes.msgnr` |
| Authentication заявки и отговори | `wlan.fc.type_subtype == 0x0b` |
| Association request / response | `wlan.fc.type_subtype in {0x00 0x01}` |
| Reassociation request / response | `wlan.fc.type_subtype in {0x02 0x03}` |
| Disassociation / deauthentication | `wlan.fc.type_subtype in {0x0a 0x0c}` |
| SAE authentication при WPA3 | `wlan.fc.type_subtype == 0x0b && wlan.fixed.auth.alg == 3` |

Добавяй условието за BSSID към тесните филтри, когато искаш само избраната мрежа. Полезни колони са Source, Destination, Info и `wlan_rsna_eapol.keydes.msgnr`. Полето може да се добави като колона с десен бутон върху него в Packet Details → Apply as Column.

Това са **display filters**, не capture filters: скриват пакети от изгледа, без да ограничават първоначалния запис.

## 4. Терминал: само auth и EAPOL събития

След като каналът е фиксиран и няма друг инструмент, който го сменя:

```bash
sudo tshark -i wifi_mon -n -l \
  -Y 'wlan.bssid == 02:11:22:33:44:55 && (eapol || wlan.fc.type_subtype in {0x00 0x01 0x02 0x03 0x0a 0x0b 0x0c})' \
  -T fields -E header=y -E separator=, \
  -e frame.time_relative -e wlan.sa -e wlan.da \
  -e wlan.fc.type_subtype -e wlan.fixed.auth.alg \
  -e wlan.fixed.status_code -e wlan_rsna_eapol.keydes.msgnr \
  -e _ws.col.Info
```

Показва време, адреси, тип кадър, auth алгоритъм, status code, номер на handshake съобщение и описание. Празните полета са нормални за неподходящия тип кадър. `-l` обновява изхода своевременно; `-n` изключва резолването на имена. Това е основа за бъдещ сигнал при събитие, но командата сама не изпраща известия и не записва PCAP.

## 5. Продължителен запис с ограничен размер

На вече фиксирания канал:

```bash
mkdir -p captures
sudo dumpcap -i wifi_mon -s 0 \
  -b duration:300 -b filesize:50000 -b files:12 \
  -w captures/network.pcapng
```

Сменя файла при 5 минути или около 50 MB, което настъпи първо, и пази до 12 файла — приблизително до 600 MB плюс служебни разходи. При достигане на лимита презаписва най-стария. Записва целия приет трафик на текущия канал; филтрирай при анализа. Спри с `Ctrl+C` и запази важния файл преди да бъде презаписан. Обмен близо до ротация може да е разделен между два съседни файла.

## 6. Как разбираме какво сме засекли

- **Authentication не е 4-way handshake.** При WPA2 кадрите за 802.11 authentication обичайно предхождат association и EAPOL-Key обмена; не съдържат Wi-Fi паролата.
- **Един EAPOL пакет не доказва пълен обмен.** За пълна диагностична последователност търси M1, M2, M3 и M4 между същите AP и клиент в една сесия. Разгледай времето, replay counter и повторните предавания; четири произволни пакета не са достатъчно доказателство.
- **M1–M4 не означава автоматично успешна връзка.** При проблем провери status/reason кодовете и последващите кадри. Group-key обменът също не бива да се бърка с началния pairwise handshake.
- **WPA3-SAE има различен authentication обмен.** SAE кадрите са management authentication, а след тях може да има EAPOL-Key. Само филтърът `eapol` пропуска SAE частта.
- **Enterprise мрежите имат и EAP/802.1X.** За тях анализирай и `eap`/`eapol`, а при достъп до инфраструктурата — AP и RADIUS логовете.
- **Липса на пакети не доказва липса на събитие.** Възможни са грешен канал/BSSID, слаб сигнал, загубени кадри или неподдържан обхват. Channel hopping увеличава риска да пропуснеш части от обмена.
- **Криптираните заявки на приложенията са отделна задача.** Monitor mode не разкрива автоматично HTTPS съдържание. Тук „auth“ означава Wi-Fi authentication/802.1X, не вход в уебсайт.

За по-широко постоянно наблюдение Kismet е следваща възможност: поддържа обзор на устройства, запазване на EAPOL handshake данни и PCAP експорт. За текущата задача наличните airodump-ng и Wireshark дават по-кратък път до резултат.

## 7. Приключване

Спри capture програмите, след което:

```bash
sudo ./wifi-monitor.sh stop
```

Това премахва `wifi_mon` чрез съществуващия скрипт.

## 8. Интерактивна терминална програма

Файл: `wifi-console.py`. Използва Python 3 и стандартния модул curses, без допълнителни Python пакети.

```bash
sudo ./wifi-monitor.sh start
sudo ./wifi-console.py
```

Избирай с ↑/↓ и потвърждавай с Enter. Първа опция: „Запис на пакети (dumpcap)“. В нея има „Старт“, „Стоп“ и „Назад“. Q връща назад или излиза от главното меню. Назад, изходът и Ctrl+C спират текущия запис и опитват да приберат файловете.

Програмата показва общия брой записани пакети, докладван от dumpcap, размерите на наличните файлове, процента от лимита, текущия/последния файл и папката за съхранение. Броячът е за сесията и може да включва пакети от вече презаписани файлове. Процентът е спрямо лимита за размер; ротация настъпва и при изтичане на 300 секунди, дори файлът да не е пълен. При малък терминал се виждат само последните файлове; разшири прозореца за повече информация.

Записът първо е в отделна root папка `/tmp/wifi-capture-ДАТА_ЧАС_МИЛИСЕКУНДИ-СЛУЧАЕН_СУФИКС`. След спиране файловете се копират в отделна сесийна подпапка на `captures` до програмата и собствеността се задава на потребителя, стартирал sudo. Имената на базовия PCAPNG включват местна дата, час, секунди и три цифри за милисекунди; dumpcap добавя свой пореден номер и време при ротация. Случайният суфикс предпазва от съвпадение и при два старта в една милисекунда.

При неуспешно копиране оригиналите остават във временната папка и грешката показва пътя. Не започва нова сесия, докато предишната не бъде прибрана успешно. При аварийно изключване или SIGKILL автоматичното прибиране не е гарантирано; `/tmp` може да бъде изчистен при рестарт.

Програмата използва текущия канал на `wifi_mon` и не го сменя. Не стартирай паралелно channel hopping върху същото радио. Ротацията остава 300 секунди / 50000 kB / 12 файла.

Проверка на програмата: компилация на Python и симулиран процес за start → брояч/размер → stop → копиране → нова уникална сесия. Реален запис през менюто предстои да бъде проверен на машината с sudo.

### Обновяване: филтриран запис без презаписване

Текущата `wifi-console.py` вече използва capture filter: записва само authentication, association/reassociation, deauthentication/disassociation и EAPOL (включително EAPOL-Key handshake). Beacon, обичайните data кадри и probe заявки не се записват. Филтърът важи за всички приети мрежи на текущия канал, без ограничение по BSSID.

Премахнат е `-b files:12`: ротацията остава 300 секунди или 50000 kB, но броят файлове е неограничен и старите не се презаписват. Това заменя предишното описание на лимита за интерактивната програма; самостоятелните dumpcap примери по-горе все още показват стария ограничен вариант. Записът приключва при Стоп или грешка, включително запълнен диск.

След успешно прибиране временните копия в /tmp се премахват; записите в captures остават. При неуспешно прибиране оригиналите се запазват в /tmp.

### Два отделни режима в менюто

Първата опция отново записва всички пакети; втората записва само auth/association/EAPOL и кадри за прекъсване. И двата режима са без лимит на броя файлове и без презаписване. Екранът показва избрания режим. Цветовете са бяло върху черно, с бяло върху тъмносиво за избрания ред при терминал с 16/256 цвята.

### Избор на канал

В двата режима вече има бутон „Канал“ до Старт/Стоп/Назад. Показва текущия канал. Изборът предлага основните 1, 6, 11, 36, 40, 44, 48, 149, 153, 157, 161, когато адаптерът ги поддържа, плюс ръчно въвеждане и запазване на текущия канал. Списъкът се превърта със стрелките.

Ръчният номер се проверява срещу каналите на конкретното радио от iw; disabled каналите се изключват. Смяната се прави по съответната честота. При отказ от драйвера се показва грешката. Канал се сменя само при спрян запис. Няма channel hopping. Изборът важи и за другите интерфейси върху същото радио.

Проверени са откриването на каналите на локалния адаптер, изключването на disabled каналите и Python синтаксисът. В рамките на проверката не е сменян реално каналът.

### Плоска папка и поредни номера

Всички записи вече се прибират директно до `wifi-console.py`, без подпапки. Имената започват с шестцифрен пореден номер на сесия и местна дата/час до секунди, например `000007_2026-10-29_21-30-00_00001_20261029213000.pcapng`. Последните части се добавят от dumpcap за файловете при ротация. Милисекунди няма. Поредният номер се пази в `.wifi-record-number` с файлово заключване; статистиката показва само текущата сесия. Съществуващите шест записа са преместени в главната папка и преименувани.

AppArmor разрешението за TShark също трябва да покрива новото място. В `/etc/apparmor.d/local/tshark` добави:

```text
owner "/path/to/wifi-bee/*.pcapng" r,
```

След това презареди с `sudo apparmor_parser -r /etc/apparmor.d/tshark`. Старите правила за captures могат да останат.

### Уточнение на местоположението

Крайното местоположение е `captures/` до програмата, без сесийни подпапки. Съществуващите номерирани записи са преместени там. Поредните номера и имената без милисекунди остават. Предишното указание за запис директно до програмата е заменено с това уточнение. Съществуващото AppArmor правило за `captures/**.pcapng` покрива това местоположение; допълнителното правило за главната папка не е необходимо.

### Ротация само по размер

В интерактивната програма е премахнато условието `duration:300`. Нов файл се създава само при достигане на `filesize:50000` (около 48.83 MiB). Няма лимит на броя файлове и няма презаписване. При Стоп последният файл може да остане частично запълнен. Това заменя предишните описания на времева ротация за програмата.

### Канал в името

Новите записи включват реалния канал, прочетен от `wifi_mon` при Старт: `000008_ch-1_2026-10-29_22-00-00…pcapng`. Старите файлове запазват имената си. Ако текущият канал не може да бъде определен, програмата показва грешка и не започва запис.

### Без автоматично заспиване по време на запис

При Старт dumpcap се изпълнява чрез `systemd-inhibit --what=idle:sleep --mode=block`. При Стоп/Назад/изход групата процеси получава сигнал за спиране и блокировката се освобождава. Няма постоянна промяна на настройките за захранване. Ако inhibitor не може да бъде получен, dumpcap не се стартира и грешката се показва в конзолата. Екранът може да изгасва. Затваряне на капака и принудително/администраторско заспиване не са гарантирано блокирани.

Локалните GNOME настройки при проверката бяха suspend след 3600 секунди бездействие на зарядно. Проверено е реално получаване и освобождаване на inhibitor със симулиран запис, без радиозапис или реално заспиване.
